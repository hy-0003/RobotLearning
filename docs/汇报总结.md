## 一、已完成内容

### 1.1 系统整体概览

我们构建了一套完整的多机械臂调度智能体系统，核心架构如下：

```
MRTA-Benchmark 数据集 → TaskPlanner(LLM) → SchedulingSolver(析取图算法)
                              ↓
                       CodeGenerator(LLM) → MockSimulator(沙箱执行)
                              ↓
                       Harness 闭环反馈（最多 3 轮迭代）
                              ↓
                       Evaluator(4项指标) → 技术报告自动生成
```

**核心模块清单（共 10 个模块）**:

| 模块 | 文件 |
|------|------|
| 数据转换器 | `src/mrta_converter.py` |
| LLM 任务规划器 | `src/task_planner.py` |
| 析取图调度求解器 | `src/scheduler.py` |
| LLM 代码生成器 | `src/code_generator.py` |
| 沙箱代码执行器 | `src/code_executor.py` |
| Mock 仿真器 | `src/simulator.py` |
| Harness 闭环控制器 | `src/harness.py` |
| 对比评估器 | `src/evaluator.py` |
| LLM 接口层 | `src/llm_interface.py` |
| 技术报告生成器 | `src/gen_report.py` |

### 1.2 Harness 闭环框架（已完整实现）

完整实现了任务要求中描述的全部 Harness 模块：

| 模块 | 实现方式 |
|------|---------|
| **任务分解** | TaskPlanner：LLM 根据场景配置将自然语言指令分解为操作→机器人分配方案 |
| **资源分配** | SchedulingSolver：析取图 + LPT 启发式 + BFS 环检测 + 运输感知，纯算法求解 |
| **结果验证** | Simulator + CodeExecutor：时间步同步仿真，资源冲突实时检测 |
| **异常处理** | Harness：执行失败 → LLM 分析根因 → 生成调整策略 → 重规划（最多 3 轮） |

**闭环反馈机制已生效**（以数据集 000009 为证）:
- 第 1 次迭代 arm_0 代码含 `hasattr()` 错误 → 仿真报告 6 个操作失败
- LLM 分析根因："沙箱禁止 hasattr() 函数"
- LLM 给出调整建议："使用 is not None 替代"
- 第 2 次迭代代码修正 → 全部 25 个原语执行成功

### 1.3 数据集与评估

- **数据集**: MRTA-Benchmark，使用了 10 个场景实例（`problem_instance_1p_000000` ~ `000009`）
- **场景规格**: 每个场景 8 个操作节点、3 台机械臂、10 个工位、3 个工件（远超要求的 4 操作节点、2 工件）

- **评估指标**: makespan、任务成功率、资源利用率、约束违反次数（4 项，超过要求的至少 3 项）

## 三、遇到的问题与解决方法

### 3.1 API 错配问题

| 问题 | 现象 | 解决方案 |
|------|------|---------|
| LLM 代码使用 dict 式访问 `robot_state['key']` | `TypeError: 'SimpleNamespace' object does not support item assignment` | 创建 `FlexState` 类，支持 `.attr` 和 `['key']` 双模式访问 |
| FlexState 自动创建嵌套对象导致比较错误 | `TypeError: '<' not supported between instances of 'FlexState' and 'int'` | 改为返回 `None` 而非自动创建嵌套 FlexState |
| `main.py` 属性名不匹配 | `AttributeError: 'Operation' object has no attribute 'operation_type'` | `op.operation_type` → `op.type`，`op.dependencies` → `op.predecessors`，`e.transit_time` → `e.distance` |

### 3.2 时间计算不准确问题

| 问题 | 现象 | 解决方案 |
|------|------|---------|
| `robot_state.last_time` 永为 0 | LLM 代码 `wait(start_time - elapsed)` 中 `elapsed` 始终为 0，导致时间逻辑错误 | 在 5 个原语（move/pick/place/operate/wait）末尾均添加 `robot_state.last_time = virtual_clock[0]` |
| 协作任务被误判为工位冲突 | 两个机器人同时执行同一工件操作触发冲突检测 | `code_executor` 新增 `collaborative_workpieces` 集合，协作工件自动跳过工位冲突检测 |

### 3.3 甘特图绘制错误

| 问题 | 现象 | 解决方案 |
|------|------|---------|
| 甘特图时间轴比例错误 | 运输时间未计入，导致甘特图比实际 makespan 短 | 新增 `_compute_transport_timeline` 方法，将 depot→操作工位→depot 运输时间纳入 makespan |
| 评估报告字段名不匹配 | `gen_report.py` 显示"迭代 ?" | `it.get('iteration')` → `it.get('iteration_num')`，并在多处同步修复 |
| 报告评分显示错误 | 评分显示为 0-1 的小数而非 0-100 | 输出格式从 `{score:.2%}` 改为 `{score:.1f}/100` |

### 3.4 Prompt 迭代优化

| 迭代 | 问题 | 解决方案 |
|------|------|---------|
| **v1** | 假 100/100 评分：协作任务的 `robot_assignments` 从 `Dict[str,str]` 改为 `Dict[str,List[str]]`；FIFO 改为 LPT 启发式 | 评分回到真实的 80/100 |
| **v2** | Mock 模式 LLM 返回空 JSON，输出 0 个操作 | MockLLM 改为根据 prompt 内容智能生成 task plan 和 behavior code |
| **v3** | LLM 不知道 world_state 有哪些可用字段 | code_generator 系统提示中显式列出 robot_state 和 world_state 的所有字段 |
| **v4** | LLM 生成代码不遵守时间窗 | 系统提示从"不需要 wait"改为"必须先 wait 到 start_time 再执行" |
| **v5** | LLM 不知道操作对应的工位/工件 | 用户提示中注入每个操作的工位与工件映射 `_resolve_operation_location()` |
| **v6** | 重规划时 LLM 不知道上一次的失败原因 | harness 新增 `failure_context` 参数，`_replanning_phase` 存储 LLM 分析结果并拼入新指令 |

### 3.5 环检测导致调度死锁

| 问题 | 现象 | 解决方案 |
|------|------|---------|
| 析取边选择导致有向环 | 调度求解器在某些拓扑下生成不可行解（循环依赖） | 用 BFS `_has_path()` 检测传递路径，再添加析取边前先判断是否会形成环，防止死锁 |

### 3.6 Isaac Lab 仿真接口接入尝试（失败）

#### 尝试过程

1. **环境搭建**: 成功安装了 Isaac Lab（基于 NVIDIA Omniverse 的机器人仿真框架，前身为 Isaac Sim）
2. **基本运行**: 成功运行了 Isaac Lab 自带的示例场景（如 `franka_lift` 等官方 demo），证明安装和环境配置无误
3. **场景搭建失败**: 尝试在仿真环境中构建产线工厂场景（包含工位、工件、机械臂等），未能成功

#### 失败原因分析

| 原因 | 说明 |
|------|------|
| **个人不熟悉** | Isaac Lab / Omniverse 的 USD（Universal Scene Description）场景搭建、Prim 层级结构、物理属性配置等需要较深入的学习曲线。个人此前没有此类仿真经验 |
| **仿真环境不完善** | Isaac Lab 虽然是较新的框架，但其文档主要以机器人强化学习任务为主，缺少直接可用的"工业产线多机械臂调度"场景模板。没有开箱即用的工厂场景 |
| **开源资料匮乏** | 科研界和工业界目前没有可直接使用的开源工厂仿真项目。虽然 MRTA-Benchmark 提供了数据层面的标准，但与该数据集配套的 3D 可视化环境不存在。要搭建一个包含 10 个工位、3 台机械臂、3 个工件的产线场景，需要从零建模每个设备、工具、工件的 3D 模型和碰撞体 |
| **GPU 资源不足** | 个人电脑 GPU 显存仅 8GB。Isaac Lab 的 PhysX 物理引擎 + 渲染管线在加载多机械臂场景时显存开销较大。尝试搭建时出现显存不足警告，部分材质和纹理无法正常渲染 |
| **时间投入产出比** | 在有限时间内，完成 3D 场景建模 + 仿真接口对接 + 调试的工作量远超预期，远大于核心算法框架开发的工作量 |

#### 尝试过的方法

1. 安装 Isaac Lab 官方环境 → 成功
2. 运行官方示例场景 → 成功
3. 尝试修改示例场景添加多个机械臂 → 机械臂显示但无工位和工件
4. 尝试从 USD 模板搭建工厂场景 → 模型不显示或显示异常
5. 搜索开源工厂仿真 USD 资产 → 未找到适合的现成资源

### 4.2 核心经验教训

**技术层面**:

1. **Prompt Engineering 是关键瓶颈**: 从 v1 到 v6，经历了 6 轮 prompt 迭代才使 LLM 稳定生成正确的行为代码。最关键的改进是：1.显式列出可用字段 2.强制时间窗遵守 3.注入工位映射 4.传递失败上下文
2. **纯算法 + LLM 的混合架构是有价值的**: 析取图调度完全由算法求解，既保证了确定性和可靠性，又避免了 LLM 做数学计算的不可靠性。LLM 只负责它擅长的部分——语义理解、任务分解、代码生成和错误分析
3. **FlexState 是双刃剑**: 为了兼容 LLM 的 dict 访问习惯而设计，但自动创建属性曾导致隐蔽的比较错误。最终通过返回 None 而非自动创建对象修复
4. **时间同步是仿真核心**: `robot_state.last_time` 的同步问题曾导致所有 LLM 代码逻辑错误。这个教训说明仿真引擎中共享状态的更新必须原子化、自动化

**工程层面**:

1. **端到端测试比单元测试更重要**: 5 个 test_*.py 文件覆盖了关键路径，但真正暴露问题的是 `run_batch.py` 的批量对比。假 100/100 评分就是在批量对比中发现的
2. **报告系统是调试利器**: 从会话 JSON 到技术报告的完整链路，让每次运行的调试信息都可追溯。8 章节报告包含了 LLM 的完整推理链，这对理解 LLM 行为至关重要

**仿真可视化层面**:

1. **Isaac Lab 不适合快速原型**: Isaac Lab 的优势在于强化学习训练而非场景快速搭建。对于调度算法验证项目，Mock 仿真能更高效地暴露算法问题
2. **3D 仿真成本被低估**: 从零搭建一个工业产线场景（3 机器人 + 10 工位 + 3 工件 + 运输路径）的工作量相当于一个独立项目。在缺乏现成资产库的情况下，个人难以在短时间完成
3. **开源生态空白**: MRTA-Benchmark 提供了完美的数据基准，但没有配套的 3D 可视化环境。这是一个生态缺口，如果有类似 gym 的标准化 3D 工厂环境，研究门槛将大幅降低

### 4.3 最终结语

本项目成功实现了一个完整的 LLM + Harness 闭环多机械臂调度智能体系统，在 MRTA-Benchmark 10 数据集上取得了 **82/100 的综合评分，100% 成功率，零约束违例**。系统的工程完整度高——从数据加载、LLM 规划、算法调度、代码生成、沙箱执行到自动报告生成，形成了一条完整的工具链。

在 Isaac Lab 仿真可视化方面未能达成目标，主要受限于个人学习曲线、开源生态空白和硬件资源不足。但这并不影响核心框架的有效性验证——Mock 仿真已经完整覆盖了资源冲突检测、时间同步、协作任务处理和闭环纠错等关键机制。

如果项目要求允许以 Mock 仿真 + 甘特图可视化作为汇报材料，当前系统已经可以充分展示 LLM 驱动的 Harness 闭环智能体在多机器人调度领域的创新性和实用性。
